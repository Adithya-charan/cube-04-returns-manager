# CUBE Returns Manager: Architecture

> **Implementation status (2026-10-01):** This document's design sections describe intended boundaries, not proof that every feature is connected. In the current code, QR identifiers are manually typed; standalone authentication results are not bound to inspection records and client-supplied results are ignored by the decision engine. There is no barcode camera/scanner or hidden-marker implementation. Image quality checks do not detect blur/glare/exposure/framing, and camera hardware has not been tested. Ollama/Qwen3-VL is configured, but its real-image request timed out at 300 seconds in the local test. S3-compatible storage exists, but the Ollama provider expects local paths, so remote storage is not end-to-end integrated. The API has no user authentication/authorization; tenant IDs are caller-supplied and do not establish identity.

The current source of truth for verified behavior is `README.md` and the test suite. Sections below should be read as architectural intent wherever they exceed that verified state.

## 1. System Responsibilities
The Returns Manager is responsible for assessing the identity, completeness, condition, and next-step disposition of returned physical parcels. Its primary output is a structured, evidence-backed decision record for downstream processing by the Recovery Manager.

## 2. Input Data Flow
Data enters the Returns Manager as a returned parcel event containing:
- Operational references (`unit_id`, `record_id`, `org_id`, `order_id`, `ordered_sku`, `ordered_asin`, `parts_list`).
- Visual and operator evidence (images defined in `photo_refs`, plus any provided contextual observations).

The flow is batched where appropriate to minimize latency and API costs:
`Input Parsing -> Vision Layer (Observation Extraction) -> Decision Layer (Rule Evaluation) -> Evidence Output Generation`

## 3. Photo/Evidence Handling
Pluggable Vision Integration: The system ingests images specified in `photo_refs`. Given that an absence of a feature in an image does not conclusively prove physical absence, the system handles visual evidence using explicit confidence measures. Observations generated by the vision output evaluate features uniquely as `OBSERVED`, `NOT_OBSERVED`, or `UNCERTAIN`.

## 4. Identity Verification
Checks whether the returned item matches the expected `ordered_sku` and `ordered_asin`.
- Compares visual evidence against abstract product expectations (designed for unseen products rather than a hardcoded product list).
- Outputs `PASS`, `FAIL`, or `UNCERTAIN` for identity lock.

## 5. Completeness Verification
Extracts the expected parts from `parts_list` (e.g., `puzzle pieces;poster`, `lamp;usb cable;manual`) and locates them via the Vision layer.
- Sub-components evaluated as missing in images are treated as `NOT_OBSERVED`. Unless corroborated by definitive physical proof, this often triggers an `UNCERTAIN` state for completeness, prompting human review.

## 6. Condition Assessment
The condition must be strictly graded on the authoritative Amazon Condition Scale (e.g., *New*, *Used - Like New*, *Used - Very Good*, *Used - Good*, *Used - Acceptable*, *Unacceptable*).
- The raw `observed_state` provided in input (e.g. `opened_unused`, `signs_of_use`, `damaged`) and the visual evidence are evaluated against the official Amazon rules.
- The system will NOT invent condition categories.

## 7. Disposition Decision
Based on Identity, Completeness, and Condition, the agent recommends a disposition: `restock`, `refurbish`, `liquidate`, `dispose`, or `pending_review`.
- Ambiguous identity or rule application always defaults to `pending_review` via `UNCERTAIN` outcomes to prevent incorrect automated commercial actions.

## 8. Uncertainty and Pending-Review Handling
Any missing data, model boundary timeout, contradictory evidence, or low-confidence check transitions that specific decision to `UNCERTAIN`.
- **Fail Open**: Instead of discarding the record, the system safely retains partial information, flags it as `UNCERTAIN`, and transitions the record to `pending_review`.

## 9. Human Override Handling
Overrides are treated as first-class data. If an operator overrides an automated decision (e.g., the recorded `operator_disposition` conflicts with the agent disposition):
- The system fully preserves the original AI verdict.
- The revised verdict, operator label (`operator_id`), and reason for override are captured within the `overrides` section of the evidence contract.

## 10. Evidence/Decision Record
The system outputs a structured JSON contract strictly adhering to the official cross-pod schema required by the Recovery Manager:
- **Base Attributes**: `record_id`, `schema_version`, `organization_id`, `client_id`, `agent`, `subject`, `captured_at`, `operator_label`, `images`.
- **Checks Array**: Discrete evaluation for Identity, Completeness, and Condition. Each check includes `check_key`, `verdict` (`PASS`/`FAIL`/`UNCERTAIN`), `confidence`, `detail`, `model_version`, and `latency_ms`.
- **Outcome Variables**: `outcome` (Disposition), `overrides`, `status`, and `content_hash`.

## 11. Multi-Tenant Isolation
Organization and client data must remain strictly isolated logically using `org_id` (e.g. `org_demo_alpha` vs `org_demo_bravo`).
- Data access patterns mandate `org_id` as the primary scoping key to prevent cross-account leakage.
- Evidence paths (like images) cannot be accessed directly without verifying tenancy.

## 12. Cross-Pod Interoperability
The system strictly enforces the official Returns Manager evidence contract layout to ensure downstream compatibility with the Recovery Manager. The common `unit_id` maintains the thread of the item's operational lifecycle.

## 13. Database Entities and Relationships
- **ReturnRecord**: Root entity tracking `record_id`, `unit_id`, `org_id`, `order_id`, and timeline.
- **EvidenceCheck**: One-to-many relationship with `ReturnRecord`, tracking atomic rule decisions (Identity, Completeness, Condition).
- **VerdictOverride**: Stores `original_verdict`, `new_verdict`, `operator_id`, and `reason`.

## 14. Backend API Boundaries
The architecture incorporates an HTTP-based ingestion endpoint.
- **`POST /agent`**: Triggers processing for a return event payload.
- **`GET /health`**: General application status indicating service and dependency readiness.

## 15. Vision-Model Integration Boundary
An isolated abstraction layer interacting with multimodal AI.
- **Input**: Image paths (`photo_refs`) and focused prompt components.
- **Output**: Discrete physical observations (`OBSERVED`, `NOT_OBSERVED`, `UNCERTAIN`). It strictly classifies observed reality without forming business disposition decisions.

## 16. Decision-Engine Boundary
An isolated rule-processing domain.
- **Input**: Vision layer observations and structural operational data (`parts_list`, expected metadata).
- **Output**: Authoritative checks (Amazon condition mapping, completeness boolean, disposition). Keeps reasoning batched for efficiency.

## 17. Evaluation and Metrics Pipeline
Tracks system performance across a held-out test set (50+ unseen units):
- Computes accuracy natively against independently human-labeled truth for identity, completeness, condition, and disposition.
- Continuously exposes metrics on False Positives (FP), False Negatives (FN), `UNCERTAIN` distribution, and overall latency/cost. 

## 18. Error and Timeout Handling
A robust fail-open paradigm is mandated globally across integration nodes.
- If upstream dependencies (vision layers, databases) drop connections, the record gracefully logs the error context under the check's `detail` property and emits a fail-open `UNCERTAIN` / `pending_review` status instead of dropping operations. 

## 19. Logging and Auditability
All internal decision nodes log traces anchored by `record_id` and `unit_id`. An immutable baseline is formed mathematically utilizing a computed `content_hash` appended to final decisions.

## 20. Deployment Requirements
- Application instances are stateless and appropriately structured for containerization.
- Requires isolated environment variable pipelines for passing secret LLM/API keys.
- Local filesystem mounts are supported specifically for retrieving synthetic records (`data/returns_sample.csv`) and testing `.jpg` fixtures.

- **Ambiguity of `NOT_OBSERVED` parts**: Does lack of visual proof of internal components (e.g., hidden manual inside a box) mandate a fallback to `UNCERTAIN` resulting globally in a `pending_review` disposition, or is soft-inference allowed based on box scale/weight logic? (Assuming manual explicit proof check based on rules, meaning `UNCERTAIN` for now).
- **Condition Scale Resolution**: What are the strict translation matrices transferring the internal operational observation flags (`opened_unused`, `signs_of_use`, `damaged`) mapping definitively to the Amazon Condition Scale strings?
